The Bily API uses standard HTTP status codes and JSON error bodies.

```json
{
  "error": "Store not found"
}
```

Unexpected server errors can also include the request ID:

```json
{
  "error": "Internal Server Error",
  "requestId": "2ae61752-6902-4d1b-a54a-b9843fbed75a"
}
```

## Status codes

| Status | Meaning | Recommended handling |
| --- | --- | --- |
| `400` | Invalid path, query, or request body | Fix the request. Do not retry unchanged. |
| `401` | Missing or invalid authentication | Replace or rotate the API key. |
| `403` | The identity or key lacks access | Verify key permissions and organization scope. |
| `404` | The scoped resource was not found | Refresh organizations, stores, or resource IDs. |
| `409` | The request conflicts with current state | Read the resource and disambiguate or update the request. |
| `429` | Too many requests | Retry with exponential backoff and jitter. |
| `500` | Bily could not complete the request | Retry safe reads; investigate before retrying writes. |
| `502` | A dependent capability was temporarily unavailable | Retry safe reads after a short delay. |
| `504` | The request did not complete before its timeout | Retry safe reads after a short delay or reduce the requested range. |

## Preserve the request ID

Every response includes `x-request-id`. You may send your own safe correlation value in `x-request-id` or `x-correlation-id`; Bily returns the selected value as `x-request-id`.

```typescript
const requestId = crypto.randomUUID();
const response = await fetch(
  "https://app.bily.ai/api/customer/v1/organizations",
  {
    headers: {
      "x-api-key": process.env.BILY_API_KEY!,
      "x-request-id": requestId,
    },
  },
);

if (!response.ok) {
  const bilyRequestId = response.headers.get("x-request-id");
  const body = await response.json().catch(() => null);
  throw new Error(
    `Bily request failed (${response.status}, request ${bilyRequestId}): ${JSON.stringify(body)}`,
  );
}
```

Do not place customer data, credentials, or secrets in a request ID.

## Retry safely

Retry idempotent `GET` requests after transient `429`, `500`, `502`, or `504` responses. Use capped exponential backoff with jitter.

Do not automatically retry create, clone, update, toggle, delete, sync, or mutation requests unless your application can prove the first attempt did not succeed. Read the affected resource before deciding whether to repeat a write.
